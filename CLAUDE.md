# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Проект

Сервис вишлистов: Laravel 13 (PHP 8.3+) как API-бэкенд и Vue 3 SPA (TypeScript, Vite), которое отдаётся из того же приложения. БД — MySQL. Комментарии в коде, сообщения коммитов и документация ведутся на русском языке.

## Команды

```bash
composer dev            # server + queue:listen + pail (логи) + vite одновременно
php artisan serve       # только бэкенд
npm run dev             # только Vite
npm run build           # сборка фронтенда

npm run lint            # ESLint (.js/.ts/.vue)
npm run type-check      # vue-tsc --noEmit
npm run format          # Prettier

composer test                                  # config:clear + php artisan test
php artisan test --filter=ИмяТеста             # один тест
php artisan test tests/Feature/ExampleTest.php # один файл
vendor/bin/pint                                # форматирование PHP

php artisan migrate
php artisan l5-swagger:generate                # пересобрать storage/api-docs/api-docs.json
```

Docker (`docker-compose.yml`): nginx на порту 8876, MySQL на 3307. Локально проект также запускается через OSPanel.

Скрипты для прод-сервера лежат в `scripts/` (каталог исключён из git, на сервер копируется вручную) и запускаются там от root из корня проекта: `deploy.sh` (сборка образа и выкладка), `backup-data.sh` (дамп БД и фотографии пользователей), `restore-data.sh` (восстановление из копии `backup-data.sh`), `backup-config.sh` (`.env`, серверные Docker-файлы и конфигурация nginx, которых нет в git). Серверные `docker-compose.yml` и `_docker/app/Dockerfile` отличаются от файлов репозитория.

## Архитектура бэкенда

**Маршрутизация и аутентификация.** Используется cookie-based SPA-аутентификация Sanctum (`statefulApi()` в `bootstrap/app.php`), а не Bearer-токены. Поэтому вход, регистрация и все защищённые эндпоинты (`/v1/login`, `/v1/user`, `/v1/wishlists`…) находятся в `routes/web.php` и не имеют префикса `/api`. В `routes/api.php` (префикс `/api`) лежат только публичные эндпоинты расшаренных вишлистов. В конце `routes/web.php` стоит SPA-fallback `/{any}` → `welcome`; новые веб-маршруты добавляются **выше** него. Файл `docs/sanctum-auth-changes.md` описывает раннюю версию с Bearer-токенами и устарел.

**Слои.** Контроллер (`app/Http/Controllers/Api`) → FormRequest (`app/Http/Requests/<Домен>`) → сервис (`app/Services/<Домен>/<Домен>Service.php`, внедряется через конструктор) → Resource. Бизнес-логика находится в сервисах, контроллеры остаются тонкими.

**Формат ответов.** Успешные ответы оборачиваются в `{ success, statusCode, data }`: ресурсы наследуются от `App\Http\Resources\ApiResource` / `ApiCollection`. Ошибки для JSON-запросов приводятся к виду `{ success: false, statusCode, data: { message, errors } }` в обработчике исключений в `bootstrap/app.php`. Поэтому фронтенд читает данные из `response.data.data`, а текст ошибки — из `error.response.data.data.message`.

**Swagger.** OpenAPI-описания записаны атрибутами в отдельных классах `app/Http/Controllers/Swagger/*Controller.php`, а не в рабочих контроллерах. При изменении API нужно обновить соответствующий Swagger-класс.

**Модели.**

- `User`: первичный ключ — ULID; вход по `username`/`email`. Сессия живёт `SESSION_LIFETIME` минут бездействия; флаг `remember` при входе (чекбокс «Запомнить меня», по умолчанию включён) ставит cookie `remember_web_*` на `AUTH_REMEMBER_DAYS` дней (по умолчанию 30; ключ `remember` гварда `web` в `config/auth.php`), по которой вход восстанавливается после истечения сессии. Срок скользящий: middleware `RenewRememberCookie` на защищённых маршрутах не чаще раза в сутки на сессию выдаёт действующую cookie заново на полный срок, поэтому вход теряется только после `AUTH_REMEMBER_DAYS` дней без визитов. Смена и сброс пароля и удаление аккаунта меняют `remember_token`, чтобы прежние cookie перестали действовать на всех устройствах (при смене пароля текущее устройство получает новую cookie). Выход (`logoutCurrentDevice`) завершает вход только на текущем устройстве: его cookie удаляется, `remember_token` не меняется. Кнопка «Выйти везде» в окне настроек (`POST /v1/logout-all`, `AuthService::logoutAllDevices`) удаляет все сессии и Sanctum-токены пользователя и меняет `remember_token`, то есть выходит на всех устройствах, включая текущее. На фронтенде `lib/authInterceptor.ts` при 419 (после долгого перерыва нет cookie `XSRF-TOKEN`, и CSRF проверяется раньше входа) один раз запрашивает `GET /sanctum/csrf-cookie` и повторяет запрос, а при 401 у вошедшего пользователя сбрасывает его, очищает кэш Vue Query и переводит на `/login?expired=1`. Аккаунт активируется подтверждением email-кода (`VerificationRegistrationCode`, письмо `VerificationCodeMail`). Пароль восстанавливается кодом из письма (`PasswordResetCodeMail`); хеш кода хранится в стандартной таблице `password_reset_tokens`, новый код заменяет предыдущий. Email меняется в два шага (`UserService`): `POST /v1/user/email` с новым адресом и текущим паролем отправляет код на новый адрес (`EmailChangeCodeMail`), `POST /v1/user/email/confirm` с кодом применяет адрес. Незавершённый запрос хранится в `EmailChangeRequest` (один на пользователя, новый заменяет прежний, хеш кода, 15 минут, после 5 неверных попыток удаляется). При подтверждении адрес заново проверяется на занятость (409), удаляется код восстановления пароля для прежнего адреса, а на прежний адрес уходит `EmailChangedMail`; сессии не завершаются. Фон приложения `background` — ключ из enum `AppBackground` (по умолчанию `blossom`), меняется запросом `PATCH /v1/user` из окна настроек аккаунта. Цвета фонов задаются во фронтенде (`constants/appBackgrounds.ts`, `scss/ui/appBackgrounds.scss`), список ключей продублирован в типе `AppBackground` в `types/user.ts`. Фон применяет `DashboardLayout` по `auth.user`, поэтому у гостя, в том числе на общей странице, фон всегда по умолчанию. Сейчас все фоны светлые; тёмный фон должен дополнительно задавать `--app-ink`, `--app-ink-soft` и `--app-accent` (ключи `ink`, `ink-soft`, `accent` в карте `appBackgrounds.scss`); текст, который лежит прямо на фоне, а не на карточке (заголовки страниц, шапка общего списка), берёт цвет через `var(--app-ink, var(--ink))`, и в новых таких местах нужно делать так же. Фотография пользователя загружается из окна настроек (`ProfileSection`): браузер кадрирует выбранный файл в `AvatarCropModal` (`cropperjs` 1.x) и отправляет квадрат 512×512 в JPEG на `POST /v1/user/avatar`; `DELETE /v1/user/avatar` удаляет фото. `UserService::updateAvatar` всегда перекодирует изображение (`intervention/image`, GD) в WebP 256×256 без метаданных и сохраняет на диск `public` как `avatars/{id пользователя}/{ulid}.webp`; в БД хранится только путь (`users.avatar_path`), прежний файл удаляется после записи нового пути, а при удалении аккаунта удаляется весь каталог. Ограничения запроса (`UpdateAvatarRequest`): JPEG/PNG/WebP/GIF, до 2 МБ и 4096×4096 пикселей. Адрес фото (`User::avatarUrl()`, строится от `APP_URL`) отдаётся как `avatarUrl` в ответах о пользователе и владельцу списка на общей странице; без фото везде показывается первая буква имени (`components/ui/UserAvatar.vue`). Файлы отдаёт nginx: локально через `php artisan storage:link`, на проде через `location ^~ /storage/` с `alias` на `storage/app/public/`.
- `Wishlist` → `WishlistItem`. Тип списка `type` — enum `WishlistType`: `gift` (список желаний, по умолчанию), `todo` (список дел) или `note` (заметка). Тип задаётся только при создании. У заметки нет названия (`title` = null), позиций и режима сюрприза: её текст хранится в колонке `content` (до 5000 символов, у списков — null). `CreateWishlistRequest` отклоняет для заметки `title`/`items`/`hideSelections`, а для списков — `content`; при изменении заметки `WishlistService` сохраняет только `color` и `content`. Заметка по ссылке недоступна никогда. У списка дел `is_selected` позиции означает «выполнено» (владелец отмечает дело с карточки через `PATCH /v1/wishlists/{id}/items/{itemId}`, для списка желаний он отвечает 422; снятие отметки гостя карточка сначала подтверждает строкой под делом, потому что автор отметки при этом стирается); ссылки, цены, приоритета и режима сюрприза у него нет (`CreateWishlistRequest` их отклоняет, `WishlistService` очищает при изменении). Флаг `is_shared` (`isShared` в API) открывает список по ссылке. У списка желаний он по умолчанию включён (значение по умолчанию зависит от типа и задаётся в `Wishlist::booted()`), у списка дел — выключен; выключенный флаг скрывает список желаний от гостей: общая страница и все публичные эндпоинты (выбор, брони, совместный подарок) отвечают 404, а брони и совместные подарки сохраняются и возвращаются при повторном открытии. Список дел по ссылке открывается только для просмотра: `GET /api/v1/shared-wishlists/{id}` отдаёт его с полем `type: todo`, а эндпоинты выбора, броней и совместного подарка (`SharedWishlistService::sharedQuery()`) отвечают для него 404. У заметки флаг всегда `false`: `CreateWishlistRequest` его отклоняет, `WishlistService` игнорирует при изменении. Условие открытия по ссылке — `Wishlist::isShared()` и scope `openByLink()`. Карточка в дашборде показывает значок у общего списка дел и у скрытого списка желаний. Флаг `guests_can_check` (`guestsCanCheck`, по умолчанию `false`, тоже только у списка дел) при включённом `is_shared` разрешает любому гостю отметить дела выполненными через `POST /api/v1/shared-wishlists/{wishlist}/items/check` (`SharedWishlistService::checkTodoItems`, иначе 404); уже выполненные дела не меняются, снять отметку гость не может. В ответе общей страницы `guestsCanCheck` — действующее разрешение (`Wishlist::guestsCanCheck()`), владельцу отдаётся сохранённое значение. Флаг `guest_name_required` (`guestNameRequired`, по умолчанию `true`) требует от гостя имя в поле `name` этого запроса (до 50 символов; без имени 422). Автор отметки хранится у позиции: `checked_by_guest` и `checked_by_name` (имя гостя или null); владелец, ставя или снимая отметку (`setItemSelected`, `syncItems`), сбрасывает их, а повторная отметка гостем уже выполненного дела их не меняет. В API у позиций списка дел есть `checkedBy`: `null` у невыполненного дела, иначе `{ guest, name }` (`WishlistItemResource::withCheckedBy()`). Общая страница подписывает отметки владельца его `username`, карточка владельца подписывает отметки гостей их именами, а собственные отметки владельца — словом «Вы» (как и свои отметки гостя на общей странице, оно выделено зелёным: признак `isOwn` у `TodoCheckedBy`), если гостям разрешено отмечать дела или в списке остались их отметки; имя гость вводит в `TodoGuestNameModal`, оно хранится в `localStorage` (`todo-guest-name`). Дела, отмеченные гостем из этого браузера, общая страница подписывает словом «Вы» (`composables/useGuestTodoChecks.ts`): после отметки в `localStorage` (`todo-checked:{id списка}`) запоминаются id дел и имя, под которым их отметили, а «Вы» показывается, пока отметка гостевая и имя совпадает; дела, с которых отметку сняли, забываются при загрузке списка. На бэкенде признака «своей» отметки нет. Дубликат списка дел создаётся без доступа по ссылке, но с прежними `guestsCanCheck` и `guestNameRequired`; дубликат списка желаний открыт по ссылке. Дата списка `due_date` (`dueDate`, только дата `Y-m-d`, необязательна, 2000–2099) у списка дел означает срок «Сделать до», у списка желаний — дату события; у заметки её нет (`CreateWishlistRequest` отклоняет, `WishlistService` игнорирует при изменении), `null` в `PATCH` убирает дату. Она отдаётся и владельцу, и на общей странице. Число оставшихся дней считает фронтенд по местной дате пользователя (`lib/dueDate.ts`): карточка в дашборде показывает плашку («Осталось 5 дней», «Срок сегодня», «Просрочено на 2 дня», у списка желаний «Через 12 дней»), общая страница — строку под шапкой. У выполненного списка дел счётчика нет, у списка желаний после события он скрывается. Дубликат получает дату источника, только если она ещё не прошла. Цвет списка `color` — ключ из enum `WishlistColor`; он отдаётся и на общей странице, где им окрашена карточка списка, а тень карточки в дашборде берёт насыщенный оттенок цвета (`glow` в `wishlistColors.scss`, у белого — нейтральная серая); сами оттенки задаются во фронтенде (`constants/wishlistColors.ts`, `scss/ui/wishlistColors.scss`), а список ключей продублирован в типе `WishlistColor` в `types/wishlist.ts`, поэтому новый цвет добавляется во все эти места.
- `WishlistItem`: в БД название позиции хранится в колонке `description`, а в API и на фронтенде называется `label`. Порядок позиций хранится в `position` и задаётся порядком массива `items` в запросе. Необязательные поля: `urls` — до трёх ссылок на товар (JSON-колонка; только http(s), каждая до 2048 символов; пустые элементы `WishlistService` отбрасывает, без ссылок в БД `null`, а в API пустой массив; фронтенд дописывает `https://` к адресу без схемы), `priority` (enum `WishlistItemPriority`, 1–3) и `price` (целые рубли 0–10 000 000). `null` в `priority` и `price` означает «не указано». Приоритет и цена видны и в режиме сюрприза.
- Гости по ссылке отмечают позиции через `is_selected` (`SharedWishlistService` обновляет их в транзакции и отклоняет уже выбранные позиции). Флаг `hide_selections` (режим сюрприза) убирает `isSelected` из ответов владельцу; у нового списка желаний он включён, если в запросе не передан `hideSelections` (`WishlistService::createWishlist`), а в БД и модели по умолчанию `false`; при редактировании списка выбор гостей сохраняется за позициями по `id`. Владелец списка желаний отметки не ставит: `isSelected` в `items` при изменении учитывается только у списка дел. Окно редактирования при открытии запрашивает `GET /v1/wishlists/{id}/selections`: он возвращает `checkedAt` (серверное время запроса) и `itemIds`, которые в режиме сюрприза отдаются только с `?reveal=1` (окно передаёт его, когда владелец выключает режим в окне). Владелец снимает выбор гостя запросом `DELETE /v1/wishlists/{id}/items/{itemId}/selection` с `checkedAt` (`WishlistService::clearItemSelection`), который выполняется сразу, без сохранения формы; запрос удаляет бронь позиции и совместный подарок. Если бронь создана не раньше `checkedAt`, позицию выбрали после открытия окна, и сервер отвечает 409, не снимая выбор; окно тогда заново запрашивает выбор. Ответ не зависит от того, была ли позиция выбрана, поэтому в режиме сюрприза владелец освобождает позицию вслепую (кнопка «⋯» с подтверждением), а без режима — кнопкой «Снять выбор» у выбранной позиции. Позиции при редактировании изменяются на месте по `id` (`WishlistService::syncItems`), а не пересоздаются.
- `WishlistReservation`: каждое сохранение выбора гостем создаёт бронь, выбранные позиции ссылаются на неё через `reservation_id`. В БД хранится только SHA-256 токена; по токену из `localStorage` или из ссылки `?reservation=` гость отменяет выбор отдельных позиций.
- `WishlistJointGift` (совместный подарок): гость, выбирая позицию, может передать в `joint_gifts` имя организатора, контакт и комментарий. Запись по позиции одна, привязана к брони и удаляется при отмене выбора, при снятии отметки владельцем и при удалении позиции. Поле `jointGift` выводится только на общей странице (`WishlistItemResource::withJointGift()`); владелец его не получает ни в каком режиме. Организатор по токену брони изменяет, добавляет или убирает совместный подарок на свою позицию без отмены выбора (`PUT /api/v1/shared-wishlists/{wishlist}/items/{item}/joint-gift`, `joint_gift: null` убирает его). Деньги и реквизиты сервис не хранит.
- `SavedWishlist` (раздел «Чужие списки»): закладка вошедшего пользователя на чужой список, пара `user_id` + `wishlist_id` уникальна. `GET /v1/saved-wishlists` отдаёт сводку для карточки (`SavedWishlistResource`: владелец, название, цвет, `dueDate`, `itemsCount`, `selectedCount`, без позиций), `POST /v1/saved-wishlists/{id}` добавляет (повторно — без ошибки), `DELETE` убирает. Добавить можно только список, который открывается по ссылке (scope `Wishlist::openByLink()`, его же использует `SharedWishlistService::getWishlistById`), и только чужой (свой — 422). Если владелец потом закрыл доступ к списку, закладка остаётся с `available: false` и без полей списка; удаление списка удаляет закладки каскадом, а удаление аккаунта (`UserService::deleteAccount`) — явно, так как запись пользователя остаётся. Владелец не узнаёт, кто добавил его список. На фронтенде раздел — страница `/saved` (`components/saved/`, пункт «Чужие списки» в шапке), кнопка «Добавить к себе» на общей странице — `SaveWishlistButton` (не показывается гостю и владельцу, владелец определяется по `username`), запросы — `composables/useSavedWishlists.ts`.

**Миграции.** Каталог `database/migrations/_baseline/` Laravel не загружает; это архивная копия исходной схемы.

## Архитектура фронтенда

- Точка входа — `resources/js/app.ts` (Vue Router + Pinia + TanStack Vue Query); алиас `@` → `resources/js`.
- HTTP-запросы идут только через `api` из `@/lib/api` (axios с `withCredentials`, `baseURL` из `VITE_API_URL`).
- Серверное состояние обрабатывается композаблами на Vue Query (`composables/useAuth.ts`); глобальное состояние пользователя хранится в Pinia-сторе `stores/auth.ts`.
- Доступ к маршрутам задаётся через `meta.requiresAuth` / `meta.requiresGuest`; guard в `router/index.ts` один раз вызывает `auth.fetchUser()`. Публичная страница расшаренного списка открывается по `/shared-wishlist/:id` (список желаний) и `/shared-todolist/:id` (список дел, alias того же маршрута); ссылки строит `lib/sharedLink.ts`, а страница после загрузки заменяет адрес, если он не соответствует типу списка. Прежние адреса `/shared/:id`, `/shared-wishlists/:id` и `/shared-todolists/:id` перенаправляют на `/shared-wishlist/:id` с сохранением query (`?reservation=`). Публичные API-эндпоинты остаются под `/api/v1/shared-wishlists`.
- Структура: `pages/` (страницы маршрутов), `layouts/` (`LandingLayout`, `DashboardLayout`), `components/<домен>/`, общие элементы — в `components/ui/`. Стили — SCSS (`resources/scss`) и Tailwind 4.

## Стиль кода

- ESLint требует явных типов возвращаемых значений функций (`explicit-function-return-type`), запрещает `any` и сортирует импорты (`simple-import-sort`).
- Prettier: 4 пробела, одинарные кавычки, точки с запятой.
