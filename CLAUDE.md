# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Проект

Сервис вишлистов: Laravel 13 (PHP 8.3+) как API-бэкенд и Vue 3 SPA (TypeScript, Vite), которое отдаётся из того же приложения. БД — MySQL. Комментарии в коде, сообщения коммитов и документация ведутся на русском языке.

## Команды

```bash
composer dev            # server + queue:listen + pail (логи) + vite одновременно
php artisan serve       # только бэкенд
npm run dev             # только Vite
npm run build           # сборка фронтенда

npm run lint            # ESLint (.js/.ts/.vue)
npm run type-check      # vue-tsc --noEmit
npm run format          # Prettier

composer test                                  # config:clear + php artisan test
php artisan test --filter=ИмяТеста             # один тест
php artisan test tests/Feature/ExampleTest.php # один файл
vendor/bin/pint                                # форматирование PHP

php artisan migrate
php artisan l5-swagger:generate                # пересобрать storage/api-docs/api-docs.json
```

Docker локально (`docker-compose.yml`, `_docker/app/Dockerfile`, описание в `README.md`): nginx на порту 8876, MySQL на 3307, контейнеры `queue` и `scheduler`; код подключён томом, фронтенд — `npm run dev:docker` (адрес API из `.env.docker`). Адрес базы, пароль (`DOCKER_DB_PASSWORD`, по умолчанию `secret`) и `APP_URL` задаёт `docker-compose.yml` поверх `.env`, поэтому тот же `.env` подходит и для OSPanel. Локально проект также запускается через OSPanel.

Прод-сервер использует `docker-compose.prod.yml` и `_docker/app/Dockerfile.prod` (выбраны строкой `COMPOSE_FILE=docker-compose.prod.yml` в серверном `.env`): код, `vendor` и собранный фронтенд запекаются в образ `piblwish-app`, nginx работает на самом сервере, порты PHP-FPM (9090) и MySQL (3307) открыты только на `127.0.0.1`. `.dockerignore` не пускает в образ `.env`, данные MySQL и содержимое `storage`; `VITE_API_URL` передаётся аргументом сборки. Lock-файл должен проходить `npm ci` на версии npm из `node:24-alpine`.

Скрипты для прод-сервера лежат в `scripts/` (каталог исключён из git, на сервер копируется вручную) и запускаются там от root из корня проекта: `deploy.sh` (сборка образа и выкладка), `backup-data.sh` (дамп БД и фотографии пользователей), `restore-data.sh` (восстановление из копии `backup-data.sh`), `backup-config.sh` (`.env` и конфигурация nginx, которых нет в git, сами скрипты и прод-файлы Docker). `deploy.sh` ставит на `storage` каталогам 775, файлам 664: бит исполнения у файлов Git считает изменением, и `git pull` на сервере отказывается обновлять отслеживаемые файлы.

## Архитектура бэкенда

**Маршрутизация и аутентификация.** Используется cookie-based SPA-аутентификация Sanctum (`statefulApi()` в `bootstrap/app.php`), а не Bearer-токены. Поэтому вход, регистрация и все защищённые эндпоинты (`/v1/login`, `/v1/user`, `/v1/wishlists`…) находятся в `routes/web.php` и не имеют префикса `/api`. В `routes/api.php` (префикс `/api`) лежат только публичные эндпоинты расшаренных вишлистов. В конце `routes/web.php` стоит SPA-fallback `/{any}` → `welcome`; новые веб-маршруты добавляются **выше** него. Перед fallback стоит маршрут общей страницы списка (`/shared-wishlist/{id}`, `/shared-todolist/{id}`, `/shared-fund/{id}` и прежние адреса, `SharedWishlistPageController`): он отдаёт тот же `welcome`, но с мета-тегами списка для превью ссылки в мессенджерах (`SharedPageMetaService`: название, тип, владелец, число позиций и дата; у закрытого, архивного и несуществующего списка — общие теги сайта) и с `robots: noindex`. Картинка превью общая — `public/og-image.jpg` (1200×630), адреса в тегах строятся от `APP_URL`. Файл `docs/sanctum-auth-changes.md` описывает раннюю версию с Bearer-токенами и устарел.

**Слои.** Контроллер (`app/Http/Controllers/Api`) → FormRequest (`app/Http/Requests/<Домен>`) → сервис (`app/Services/<Домен>/<Домен>Service.php`, внедряется через конструктор) → Resource. Бизнес-логика находится в сервисах, контроллеры остаются тонкими.

**Формат ответов.** Успешные ответы оборачиваются в `{ success, statusCode, data }`: ресурсы наследуются от `App\Http\Resources\ApiResource` / `ApiCollection`. Ошибки для JSON-запросов приводятся к виду `{ success: false, statusCode, data: { message, errors } }` в обработчике исключений в `bootstrap/app.php`. Поэтому фронтенд читает данные из `response.data.data`, а текст ошибки — из `error.response.data.data.message`.

**Swagger.** OpenAPI-описания записаны атрибутами в отдельных классах `app/Http/Controllers/Swagger/*Controller.php`, а не в рабочих контроллерах. При изменении API нужно обновить соответствующий Swagger-класс.

**Модели.**

- `User`: первичный ключ — ULID; вход по `username`/`email`. Сессия живёт `SESSION_LIFETIME` минут бездействия; флаг `remember` при входе (чекбокс «Запомнить меня», по умолчанию включён) ставит cookie `remember_web_*` на `AUTH_REMEMBER_DAYS` дней (по умолчанию 30; ключ `remember` гварда `web` в `config/auth.php`), по которой вход восстанавливается после истечения сессии. Срок скользящий: middleware `RenewRememberCookie` на защищённых маршрутах не чаще раза в сутки на сессию выдаёт действующую cookie заново на полный срок, поэтому вход теряется только после `AUTH_REMEMBER_DAYS` дней без визитов. Смена и сброс пароля и удаление аккаунта меняют `remember_token`, чтобы прежние cookie перестали действовать на всех устройствах (при смене пароля текущее устройство получает новую cookie). Выход (`logoutCurrentDevice`) завершает вход только на текущем устройстве: его cookie удаляется, `remember_token` не меняется. Кнопка «Выйти везде» в окне настроек (`POST /v1/logout-all`, `AuthService::logoutAllDevices`) удаляет все сессии и Sanctum-токены пользователя и меняет `remember_token`, то есть выходит на всех устройствах, включая текущее. На фронтенде `lib/authInterceptor.ts` при 419 (после долгого перерыва нет cookie `XSRF-TOKEN`, и CSRF проверяется раньше входа) один раз запрашивает `GET /sanctum/csrf-cookie` и повторяет запрос, а при 401 у вошедшего пользователя сбрасывает его, очищает кэш Vue Query и переводит на `/login?expired=1`. Аккаунт активируется подтверждением email-кода (`VerificationRegistrationCode`, письмо `VerificationCodeMail`); код действует 2 минуты, после чего форма `VerificationRegistrationForm` скрывает поле ввода и предлагает кнопку «Отправить новый код» (`POST /v1/verify-registration/resend`, `AuthService::resendVerificationCode`): новый код заменяет прежний, ответ одинаков для любого email, лимит — раз в минуту на адрес. Если код так и не ввели, регистрацию можно завершить двумя путями: вход с верным паролем в неподтверждённый аккаунт отправляет новый код и отвечает 403, по которому `LoginForm` показывает ту же форму ввода кода и после подтверждения входит; повторная регистрация на тот же email не отклоняется, а перезаписывает логин и пароль неподтверждённого аккаунта (scope `User::pendingVerification()`, `RegistrationRequest` не считает его email и логин занятыми), поэтому занять чужой адрес, не подтвердив его, нельзя. Пароль восстанавливается кодом из письма (`PasswordResetCodeMail`, действует 2 минуты; `ResetPasswordForm`, как и форма кода регистрации, показывает отсчёт `composables/useCodeTimer.ts` над полем и после истечения срока скрывает поля до отправки нового кода); хеш кода хранится в стандартной таблице `password_reset_tokens`, новый код заменяет предыдущий. Email меняется в два шага (`UserService`): `POST /v1/user/email` с новым адресом и текущим паролем отправляет код на новый адрес (`EmailChangeCodeMail`), `POST /v1/user/email/confirm` с кодом применяет адрес. Незавершённый запрос хранится в `EmailChangeRequest` (один на пользователя, новый заменяет прежний, хеш кода, 15 минут, после 5 неверных попыток удаляется). При подтверждении адрес заново проверяется на занятость (409), удаляется код восстановления пароля для прежнего адреса, а на прежний адрес уходит `EmailChangedMail`; сессии не завершаются. Статистика пользователя: колонки `users.created_{gift,todo,note,fund}_count` (`User::createdCountColumn()`) считают карточки, созданные за всё время. `WishlistService::createWishlist` увеличивает счётчик в транзакции создания, поэтому учитываются и дубликаты (они создаются тем же запросом), а удаление списка счётчик не уменьшает; удаление аккаунта обнуляет счётчики. Колонок нет в `fillable`. В API это `stats: { gift, todo, note, fund }` в ответах о пользователе, его показывает `UserStatsSection` в окне настроек; после создания карточки `WishlistMain` увеличивает счётчик в сторе `auth`. Фон приложения `background` — ключ из enum `AppBackground` (по умолчанию `blossom`), меняется запросом `PATCH /v1/user` из окна настроек аккаунта. Цвета фонов задаются во фронтенде (`constants/appBackgrounds.ts`, `scss/ui/appBackgrounds.scss`), список ключей продублирован в типе `AppBackground` в `types/user.ts`. От фона зависит и градиент основных кнопок и переключателей: `DashboardLayout` ставит на `<html>` атрибут `data-app-bg`, по которому `scss/ui/appBackgroundGradients.scss` (подключён глобально в `app.scss`) переопределяет `--brand-gradient`; градиент задаётся на корне, чтобы его получили и окна, вынесенные через Teleport, и при добавлении фона его нужно задать и там — в обеих картах: для тёмной темы градиенты темнее (`$app-background-gradients-dark`, а без фона — `--brand-gradient` под `:root[data-theme='dark']` в `css/app.css`). Значок выбранного подарка и прогресс списка желаний на карточке берут `--brand-gradient-fixed` (исходный градиент из `css/app.css`) и от фона не зависят. Фон применяет `DashboardLayout` по `auth.user`, поэтому у гостя, в том числе на общей странице, фон всегда по умолчанию. У каждого фона есть тёмная версия для тёмной темы (карта `$app-backgrounds-dark` в `appBackgrounds.scss`, действует под `:root[data-theme='dark']`), поэтому новый фон задаётся в обеих картах. Светлый фон в светлой теме, который сделали бы тёмным, должен дополнительно задавать `--app-ink`, `--app-ink-soft` и `--app-accent` (ключи `ink`, `ink-soft`, `accent` в карте); текст, который лежит прямо на фоне, а не на карточке (заголовки страниц, шапка общего списка), берёт цвет через `var(--app-ink, var(--ink))`, и в новых таких местах нужно делать так же. Фотография пользователя загружается из окна настроек (`ProfileSection`): браузер кадрирует выбранный файл в `AvatarCropModal` (`cropperjs` 1.x) и отправляет квадрат 512×512 в JPEG на `POST /v1/user/avatar`; `DELETE /v1/user/avatar` удаляет фото. `UserService::updateAvatar` всегда перекодирует изображение (`intervention/image`, GD) в WebP 256×256 без метаданных и сохраняет на диск `public` как `avatars/{id пользователя}/{ulid}.webp`; в БД хранится только путь (`users.avatar_path`), прежний файл удаляется после записи нового пути, а при удалении аккаунта удаляется весь каталог. Ограничения запроса (`UpdateAvatarRequest`): JPEG/PNG/WebP/GIF, до 2 МБ и 4096×4096 пикселей. Адрес фото (`User::avatarUrl()`, строится от `APP_URL`) отдаётся как `avatarUrl` в ответах о пользователе и владельцу списка на общей странице; без фото везде показывается первая буква имени (`components/ui/UserAvatar.vue`). Файлы отдаёт nginx: локально через `php artisan storage:link`, на проде через `location ^~ /storage/` с `alias` на `storage/app/public/`.
- `Wishlist` → `WishlistItem`. Тип списка `type` — enum `WishlistType`: `gift` (список желаний, по умолчанию), `todo` (список дел), `note` (заметка) или `fund` (сбор). Тип задаётся только при создании. У заметки нет названия (`title` = null), позиций и режима сюрприза: её текст хранится в колонке `content` (до 5000 символов, у списков — null). `CreateWishlistRequest` отклоняет для заметки `title`/`items`/`hideSelections`, а для списков — `content`; при изменении заметки `WishlistService` сохраняет только `color` и `content`. Заметка по ссылке недоступна никогда. Позиции сбора — цели: у каждой ровно одна ссылка https на платформу из `config/wishlist.php` (`fund_hosts`: Т-Банк, ЮMoney, CloudTips; подходят и поддомены, проверка — правило `App\Rules\AllowedFundUrl`), а `price` означает необязательную целевую сумму до 100 000 000 ₽ (у подарка граница 10 000 000 ₽). Приоритета и режима сюрприза у сбора нет (`CreateWishlistRequest` их отклоняет, `WishlistService` очищает при изменении). `UpdateWishlistRequest` загружает тип изменяемого списка, чтобы проверить ссылки и сумму сбора. По ссылке сбор, как и список дел, открывается только для просмотра: `sharedQuery()` ограничен списками желаний, поэтому выбор, брони и совместный подарок отвечают 404. Доступ по ссылке у нового сбора включён (`Wishlist::booted()`). Во фронтенде список доменов продублирован в `constants/fundHosts.ts`, а `lib/fundUrl.ts` проверяет ссылку в форме и определяет платформу для подписи под полем, на карточке и на общей странице (кнопка «Перейти к сбору»). Целевую сумму вводит `ItemPriceInput` с `target`. Прогресса у сбора нет: сервис не знает, сколько собрано. Дата сбора называется «Сбор до», прошедший срок выводится нейтрально («Срок сбора прошёл», `lib/dueDate.ts`). У списка дел `is_selected` позиции означает «выполнено» (владелец отмечает дело с карточки через `PATCH /v1/wishlists/{id}/items/{itemId}`, для списка желаний он отвечает 422; снятие отметки гостя карточка сначала подтверждает строкой под делом, потому что автор отметки при этом стирается); ссылок, цены и режима сюрприза у него нет (`CreateWishlistRequest` их отклоняет, `WishlistService` очищает при изменении), а `priority` у дела означает важность: те же значения 1–3, но во фронтенде вместо сердец молнии и подписи «Можно отложить», «Важно», «Очень важно» (`ITEM_IMPORTANCE_LABELS` в `lib/itemPriority.ts`, признак `todo` у `ItemPriorityPicker` и `ItemPriorityIcons`); у выполненного дела молнии серые, на общей странице сортировка называется «По важности». У дела с важностью подпись `TodoCheckedBy` выводится не в строке названия, а в правой колонке второй строкой под молниями (карточка и общая страница). Флаг `is_shared` (`isShared` в API) открывает список по ссылке. У списка желаний он по умолчанию включён (значение по умолчанию зависит от типа и задаётся в `Wishlist::booted()`), у списка дел — выключен; выключенный флаг скрывает список желаний от гостей: общая страница и все публичные эндпоинты (выбор, брони, совместный подарок) отвечают 404, а брони и совместные подарки сохраняются и возвращаются при повторном открытии. Список дел по ссылке открывается только для просмотра: `GET /api/v1/shared-wishlists/{id}` отдаёт его с полем `type: todo`, а эндпоинты выбора, броней и совместного подарка (`SharedWishlistService::sharedQuery()`) отвечают для него 404. У заметки флаг всегда `false`: `CreateWishlistRequest` его отклоняет, `WishlistService` игнорирует при изменении. Условие открытия по ссылке — `Wishlist::isOpenByLink()` и scope `openByLink()`: доступ включён (`isShared()`, настройка владельца, её же отдаёт `isShared` в API) и список не в архиве. Архив: колонка `archived_at` (`archivedAt` в API), `POST /v1/wishlists/{id}/archive` переносит любой список, в том числе заметку, в архив, `DELETE` того же адреса восстанавливает его (повторный вызов ничего не меняет). `GET /v1/wishlists` отдаёт только активные списки, с `?archived=1` — архив в порядке `archived_at desc`; в обоих случаях `meta.archivedCount` содержит число списков в архиве (`ApiCollection` выводит `additional()` рядом с `data`). Архивный список доступен владельцу только для просмотра: изменение, `selections`, отметка дел и снятие выбора гостя отвечают 409 (`WishlistService::ensureNotArchived`), удаление разрешено. Кнопка «Удалить все» на странице архива после подтверждения (`WishlistArchiveClearModal`) отправляет `DELETE /v1/wishlists/archived` с `ids` карточек, которые видны в архиве (`WishlistService::deleteArchivedWishlists`): удаляются только переданные списки пользователя, которые всё ещё в архиве, поэтому список, перенесённый в архив позже, не затрагивается; маршрут стоит выше `/wishlists/{id}`. По ссылке архивный список не открывается (404 на общей странице и всех публичных эндпоинтах, закладки отдаются с `available: false`), а `is_shared`, брони и совместные подарки сохраняются и снова действуют после восстановления. Карточка в дашборде показывает значок у общего списка дел, у скрытого списка желаний и у списка желаний с выключенным режимом сюрприза (глаз); значки отмечают отступление от значения по умолчанию. Флаг `guests_can_check` (`guestsCanCheck`, по умолчанию `false`, тоже только у списка дел) при включённом `is_shared` разрешает любому гостю отметить дела выполненными через `POST /api/v1/shared-wishlists/{wishlist}/items/check` (`SharedWishlistService::checkTodoItems`, иначе 404); уже выполненные дела не меняются, снять отметку гость не может. В ответе общей страницы `guestsCanCheck` — действующее разрешение (`Wishlist::guestsCanCheck()`), владельцу отдаётся сохранённое значение. Флаг `guest_name_required` (`guestNameRequired`, по умолчанию `true`) требует от гостя имя в поле `name` этого запроса (до 50 символов; без имени 422). Автор отметки хранится у позиции: `checked_by_guest` и `checked_by_name` (имя гостя или null); владелец, ставя или снимая отметку (`setItemSelected`, `syncItems`), сбрасывает их, а повторная отметка гостем уже выполненного дела их не меняет. В API у позиций списка дел есть `checkedBy`: `null` у невыполненного дела, иначе `{ guest, name }` (`WishlistItemResource::withCheckedBy()`). Общая страница подписывает отметки владельца его `username`, карточка владельца подписывает отметки гостей их именами, а собственные отметки владельца — словом «Вы» (как и свои отметки гостя на общей странице, оно выделено зелёным: признак `isOwn` у `TodoCheckedBy`), если гостям разрешено отмечать дела или в списке остались их отметки; имя гость вводит в `TodoGuestNameModal`, оно хранится в `localStorage` (`todo-guest-name`). Дела, отмеченные гостем из этого браузера, общая страница подписывает словом «Вы» (`composables/useGuestTodoChecks.ts`): после отметки в `localStorage` (`todo-checked:{id списка}`) запоминаются id дел и имя, под которым их отметили, а «Вы» показывается, пока отметка гостевая и имя совпадает (введённое имя выводится рядом в скобках: «Вы (Иван)»); дела, с которых отметку сняли, забываются при загрузке списка. На бэкенде признака «своей» отметки нет. Дубликат списка дел создаётся без доступа по ссылке, но с прежними `guestsCanCheck` и `guestNameRequired`; дубликат списка желаний открыт по ссылке. Дата списка `due_date` (`dueDate`, только дата `Y-m-d`, необязательна, 2000–2099) у списка дел означает срок «Сделать до», у списка желаний — дату события; у заметки её нет (`CreateWishlistRequest` отклоняет, `WishlistService` игнорирует при изменении), `null` в `PATCH` убирает дату. Она отдаётся и владельцу, и на общей странице. Число оставшихся дней считает фронтенд по местной дате пользователя (`lib/dueDate.ts`): карточка в дашборде показывает плашку («Осталось 5 дней», «Срок сегодня», «Просрочено на 2 дня», у списка желаний «Через 12 дней»), общая страница — такую же плашку внизу карточки рядом с датой создания (`createdAt` отдаётся и гостю), над кнопкой и под прогрессом списка дел. У выполненного списка дел счётчика нет, у списка желаний после события он скрывается. Дубликат получает дату источника, только если она ещё не прошла. Цвет списка `color` — ключ из enum `WishlistColor`; он отдаётся и на общей странице, где им окрашена карточка списка, а тень карточки в дашборде берёт насыщенный оттенок цвета (`glow` в `wishlistColors.scss`, у белого — нейтральная серая); сами оттенки задаются во фронтенде (`constants/wishlistColors.ts`, `scss/ui/wishlistColors.scss`), а список ключей продублирован в типе `WishlistColor` в `types/wishlist.ts`, поэтому новый цвет добавляется во все эти места.
- `WishlistItem`: в БД название позиции хранится в колонке `description`, а в API и на фронтенде называется `label`. Порядок позиций хранится в `position` и задаётся порядком массива `items` в запросе. Необязательные поля: `urls` — до трёх ссылок на товар (JSON-колонка; только http(s), каждая до 2048 символов; пустые элементы `WishlistService` отбрасывает, без ссылок в БД `null`, а в API пустой массив; фронтенд дописывает `https://` к адресу без схемы), `priority` (enum `WishlistItemPriority`, 1–3) и `price` (целые рубли 0–10 000 000). `null` в `priority` и `price` означает «не указано». Приоритет и цена видны и в режиме сюрприза. У цели сбора приоритета нет, у дела он означает важность (см. выше).
- Гости по ссылке отмечают позиции через `is_selected` (`SharedWishlistService` обновляет их в транзакции и отклоняет уже выбранные позиции). Флаг `hide_selections` (режим сюрприза) убирает `isSelected` из ответов владельцу; у нового списка желаний он включён, если в запросе не передан `hideSelections` (`WishlistService::createWishlist`), а в БД и модели по умолчанию `false`; при редактировании списка выбор гостей сохраняется за позициями по `id`. Владелец списка желаний отметки не ставит: `isSelected` в `items` при изменении учитывается только у списка дел. Окно редактирования при открытии запрашивает `GET /v1/wishlists/{id}/selections`: он возвращает `checkedAt` (серверное время запроса) и `itemIds`, которые в режиме сюрприза отдаются только с `?reveal=1` (окно передаёт его, когда владелец выключает режим в окне). Владелец снимает выбор гостя запросом `DELETE /v1/wishlists/{id}/items/{itemId}/selection` с `checkedAt` (`WishlistService::clearItemSelection`), который выполняется сразу, без сохранения формы; запрос удаляет бронь позиции и совместный подарок. Если бронь создана не раньше `checkedAt`, позицию выбрали после открытия окна, и сервер отвечает 409, не снимая выбор; окно тогда заново запрашивает выбор. Ответ не зависит от того, была ли позиция выбрана, поэтому в режиме сюрприза владелец освобождает позицию вслепую (кнопка «⋯» с подтверждением), а без режима — кнопкой «Снять выбор» у выбранной позиции. Позиции при редактировании изменяются на месте по `id` (`WishlistService::syncItems`), а не пересоздаются.
- `WishlistReservation`: каждое сохранение выбора гостем создаёт бронь, выбранные позиции ссылаются на неё через `reservation_id`. В БД хранится только SHA-256 токена; по токену из `localStorage` или из ссылки `?reservation=` гость отменяет выбор отдельных позиций.
- `WishlistJointGift` (совместный подарок): гость, выбирая позицию, может передать в `joint_gifts` имя организатора, контакт и комментарий. Запись по позиции одна, привязана к брони и удаляется при отмене выбора, при снятии отметки владельцем и при удалении позиции. Поле `jointGift` выводится только на общей странице (`WishlistItemResource::withJointGift()`); владелец его не получает ни в каком режиме. Организатор по токену брони изменяет, добавляет или убирает совместный подарок на свою позицию без отмены выбора (`PUT /api/v1/shared-wishlists/{wishlist}/items/{item}/joint-gift`, `joint_gift: null` убирает его). Деньги и реквизиты сервис не хранит.
- `SavedWishlist` (раздел «Чужие списки»): закладка вошедшего пользователя на чужой список, пара `user_id` + `wishlist_id` уникальна. `GET /v1/saved-wishlists` отдаёт сводку для карточки (`SavedWishlistResource`: владелец, название, цвет, `dueDate`, `itemsCount`, `selectedCount`, без позиций), `POST /v1/saved-wishlists/{id}` добавляет (повторно — без ошибки), `DELETE` убирает. Добавить можно только список, который открывается по ссылке (scope `Wishlist::openByLink()`, его же использует `SharedWishlistService::getWishlistById`), и только чужой (свой — 422). Если владелец потом закрыл доступ к списку, закладка остаётся с `available: false` и без полей списка; удаление списка удаляет закладки каскадом, а удаление аккаунта (`UserService::deleteAccount`) — явно, так как запись пользователя остаётся. Владелец не узнаёт, кто добавил его список. На фронтенде раздел — страница `/saved` (`components/saved/`, пункт «Чужие списки» в шапке), кнопка «Добавить к себе» на общей странице — `SaveWishlistButton` (не показывается гостю и владельцу, владелец определяется по `username`), запросы — `composables/useSavedWishlists.ts`. Над карточками раздела, как и в дашборде, стоит панель `WishlistSortBar` (фильтр по типу `useWishlistTypeFilter` и сортировка `useWishlistSort`), но без сортировки по дате создания: только «По сроку» (по `dueDate`, по умолчанию, ближайшие сверху) и «По названию»; карточки без значения поля, в том числе недоступные, стоят в конце. Первым на панели стоит поиск (`components/ui/CardSearchInput.vue`): сначала видна только лупа в капсуле, оформленной как кнопка фильтра, по клику капсула расширяется вправо и в ней появляется поле ввода (на экране уже 600px — на всю строку); пустое поле сворачивается при потере фокуса, Esc очищает запрос и сворачивает поле; логика — `composables/useCardSearch.ts`, на клиенте по уже загруженным карточкам; без учёта регистра, «ё» равна «е»): в дашборде и архиве ищется название, а у заметки её текст, в «Чужих списках» — название и `username` владельца. Поиск, как и панель, показывается, когда карточек больше одной; запрос не сохраняется в `localStorage`, а если ничего не найдено, на месте карточек выводится «Ничего не найдено» с кнопкой сброса. Карточки дашборда, архива и раздела выводятся порциями по 16 (`composables/useCardPaging.ts`, кнопки «Показать ещё» и «Показать все» — `components/ui/ShowMoreButtons.vue`); смена сортировки, фильтра или поискового запроса возвращает к первой порции. В дашборде «По сроку» тоже есть, в архиве её нет. Кнопка сброса (иконка `FunnelX`) на панели появляется, когда введён запрос, выбран тип или сортировка отличается от сортировки раздела по умолчанию, и очищает запрос, возвращает «Все» и сортировку по умолчанию. Над активными карточками дашборда однострочная строка «Скоро у друзей» (`UpcomingSavedWishlists`, без подписи и ссылки на раздел, название укорачивается до 10 символов) показывает до трёх доступных чужих списков с датой в ближайшие 30 дней (отбор на фронтенде по тому же запросу); без таких списков строка не выводится. Пользователь выключает её переключателем в окне настроек (`FriendsEventsToggle`): флаг `users.show_friends_events` (`showFriendsEvents`, по умолчанию `true`) меняется тем же `PATCH /v1/user`, что и фон; запрос принимает одну или несколько настроек, непереданная не меняется.
- Напоминания о сроке: команда `wishlists:send-due-reminders` (`DueDateReminderService`) запускается планировщиком ежедневно в 09:00 по `config/wishlist.php` (`reminders.timezone`, по умолчанию Europe/Moscow; дни до даты считаются по этому поясу) и отправляет пользователю одно письмо `DueDateReminderMail` о списках, дата которых лежит в промежутке от завтра до сегодня + срок пользователя `users.reminder_days` (`reminderDays`, 1–7, по умолчанию 3 — `DueDateReminderService::DEFAULT_DAYS`, продублировано в `ReminderDaysPicker`, один для своих и чужих списков). Отбор идёт по промежутку, а не по дате ровно через срок, чтобы список, дату которого указали позже, или список после уменьшения срока не остался без напоминания. В письмо попадают свои списки (кроме заметок, архивных и выполненных списков дел) и сохранённые чужие, которые открываются по ссылке (`openByLink()`; выполненные чужие списки дел тоже пропускаются); у каждого списка указана дата («Завтра, 12 октября», «Через 3 дня, 14 октября»). Владельцу в режиме сюрприза число выбранных позиций не сообщается. Получают письма только активные подтверждённые пользователи с флагом `users.email_reminders` (`emailReminders`, по умолчанию `true`). Обе настройки меняются тем же `PATCH /v1/user`; в окне настроек это переключатель «Напоминания на почту» (общий компонент `UserSettingToggle`) и выбор срока `ReminderDaysPicker`. Отправленные напоминания записываются в `wishlist_reminders` (пользователь + список + дата), поэтому о каждом списке с данной датой письмо приходит один раз, а перенос даты даёт новое напоминание. В письме и в заголовке `List-Unsubscribe` стоит ссылка отписки `/email-reminders/unsubscribe/{user}` (`EmailReminderController`, подпись `signed:relative` без хоста и схемы): GET только показывает кнопку, отключает напоминания POST (исключён из CSRF для отписки в один клик по RFC 8058). На проде нужен запуск `php artisan schedule:run` каждую минуту (cron или контейнер с `schedule:work`), письма отправляет очередь.

**Миграции.** Каталог `database/migrations/_baseline/` Laravel не загружает; это архивная копия исходной схемы.

## Архитектура фронтенда

- Точка входа — `resources/js/app.ts` (Vue Router + Pinia + TanStack Vue Query); алиас `@` → `resources/js`.
- HTTP-запросы идут только через `api` из `@/lib/api` (axios с `withCredentials`, `baseURL` из `VITE_API_URL`).
- Серверное состояние обрабатывается композаблами на Vue Query (`composables/useAuth.ts`); глобальное состояние пользователя хранится в Pinia-сторе `stores/auth.ts`.
- Доступ к маршрутам задаётся через `meta.requiresAuth` / `meta.requiresGuest`; guard в `router/index.ts` один раз вызывает `auth.fetchUser()`. Публичная страница расшаренного списка открывается по `/shared-wishlist/:id` (список желаний) , `/shared-todolist/:id` (список дел) и `/shared-fund/:id` (сбор; оба — alias того же маршрута); ссылки строит `lib/sharedLink.ts`, а страница после загрузки заменяет адрес, если он не соответствует типу списка. Архив списков открывается по `/dashboard/archive` (маршрут `dashboard-archive`): это тот же `WishlistMain` с `archived`, пересоздаваемый при переходе между разделами (`key` в `Dashboard.vue`); ссылки «Архив N» и «Мои карточки» стоят в конце панели сортировки, в архиве справа от «Мои карточки» — кнопка «Удалить все». Запросы и перенос — `composables/useWishlistArchive.ts`: ключи кэша `['wishlists']` и `['wishlists', 'archived']`, число списков в архиве записывается из `meta.archivedCount` в отдельный ключ; перенос в архив и восстановление сразу перекладывают карточку между кэшами и выполняются по очереди (`scope`). После переноса показывается `components/ui/ActionToast.vue` с кнопкой «Отменить». Карточка с `archivedAt` (`WishlistCard`) только для просмотра: вместо «Редактировать» — «Восстановить», нет копирования ссылки, значков доступа и счётчика срока, вместо него дата переноса. Сортировка и фильтр архива хранятся в `localStorage` отдельно, в архиве кнопка даты называется «По дате архивации» и сортирует по `archivedAt`. Прежние адреса `/shared/:id`, `/shared-wishlists/:id` и `/shared-todolists/:id` перенаправляют на `/shared-wishlist/:id` с сохранением query (`?reservation=`). Публичные API-эндпоинты остаются под `/api/v1/shared-wishlists`.
- Сетки карточек дашборда, архива и «Чужих списков» при первой загрузке показывают заглушки `components/ui/CardSkeletonGrid.vue`, а фоновое обновление не скрывает карточки (вращается только иконка кнопки «Обновить»). Сетка — `TransitionGroup` с `name="card-grid"` и классом `card-grid` (стили в `scss/ui/cardGridTransition.scss`, у корня карточки должен быть класс `card`); `@before-leave="pinLeavingCard"` (`lib/gridTransition.ts`) выводит уходящую карточку из потока, чтобы соседние плавно сдвигались.
- Тема оформления (светлая, тёмная или «Как в системе», по умолчанию) хранится в браузере, а не в аккаунте: `localStorage` `app-theme`, логика — `composables/useTheme.ts`, который ставит на `<html>` атрибут `data-theme` (`light`/`dark`) и следит за настройкой системы и другими вкладками. Тот же атрибут до загрузки стилей ставит встроенный скрипт в `welcome.blade.php`, чтобы страница не мигала светлой. Вошедший пользователь выбирает тему в окне настроек (`ThemePicker`, раздел «Оформление» вместе с фоном), гость — кнопкой `components/ui/ThemeToggleButton.vue` в шапке и на лендинге. Цвета интерфейса задаются переменными в `css/app.css` (`--ink`, `--ink-soft`, `--ink-muted`, `--ink-faint`, `--surface`, `--surface-strong`, `--surface-solid`, `--surface-soft`, `--surface-border`, `--tint`, `--tint-strong`, `--overlay`, `--success`, `--danger`, `--warning`, `--fund`, `--toast-bg` и др.), их тёмные значения — под `:root[data-theme='dark']`, где светлее и `--brand-violet`/`--brand-pink`. В компонентах цвета текста и поверхностей не задаются напрямую, а берутся из этих переменных; белый `#fff` остаётся только у текста и значков на градиентных кнопках. У цветов списка тоже есть тёмные версии (`$wishlist-colors-dark` в `wishlistColors.scss`), у лендинга — свои переменные `--landing-*` в `LandingLayout`. Письма и страница отписки от напоминаний остаются светлыми.
- Структура: `pages/` (страницы маршрутов), `layouts/` (`LandingLayout`, `DashboardLayout`), `components/<домен>/`, общие элементы — в `components/ui/`. Стили — SCSS (`resources/scss`) и Tailwind 4.

## Стиль кода

- ESLint требует явных типов возвращаемых значений функций (`explicit-function-return-type`), запрещает `any` и сортирует импорты (`simple-import-sort`).
- Prettier: 4 пробела, одинарные кавычки, точки с запятой.
