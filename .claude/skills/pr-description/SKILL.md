Напиши текст для пул реквеста из `dev` в `main` на основании коммитов,
которые в него попадут. Пул реквест не создавай, выведи только текст.

Дополнительные указания (например, хеш последнего коммита main или другие
ветки): $ARGUMENTS

## Какие коммиты брать

- По умолчанию — `git log --format='%h %B' origin/main..dev` (перед этим
  `git fetch origin main`). Если в аргументах указан хеш, бери
  `<хеш>..dev`.
- Если коммитов нет, так и скажи.
- Кратко назови число коммитов перед текстом.

## Название

Перед описанием выведи название пул реквеста отдельной строкой (обычным
текстом, не в блоке кода). Название максимально короткое: 3–6 слов,
перечисление двух-трёх главных тем через запятую и «и», без точки в конце.
Образец прошлого названия: «Аккаунт, оформление списков и исправления API».

## Формат описания

Описание пишется в Markdown и выводится внутри блока кода ` ```markdown `,
чтобы разметку можно было скопировать без изменений. Образец — прошлый
пул реквест:

```markdown
## Что нового

**Аккаунт**
- Смена пароля в настройках с уведомлением на email
- Деактивация аккаунта; при входе проверяется `is_active`

**Списки**
- Выбор цвета фона списка и лоадер при сохранении
- Ссылка на товар у позиций
- Перестановка позиций в модалках

**Интерфейс**
- Адаптив для узких экранов
- Оформление выбранных позиций

**Исправления**
- JSON-ошибки возвращаются с правильным HTTP-статусом
- API-префиксы исключены из SPA-fallback
- Запросы `WishlistMain` переведены на общий клиент `api`
```

- Заголовок `## Что нового`, названия разделов — жирным (`**Аккаунт**`),
  список идёт сразу под названием раздела, без пустой строки, а между
  разделами стоит одна пустая строка.
- Имена полей, файлов и классов, которые всё же попали в текст, пиши
  в обратных кавычках.

## Правила

- Группируй изменения по смыслу, а не по коммитам: «Аккаунт», «Списки»
  (или отдельно по типам списков), «Общий доступ», «Дашборд»,
  «Интерфейс», «Исправления». Пустые разделы не выводи, новые заводи,
  только если пункты не укладываются в существующие.
- Коммиты `fix:` идут в «Исправления», если это исправление ошибки, а не
  доработка возможности.
- Пиши только самое главное: обычно 2–5 пунктов в разделе, каждый пункт —
  одна короткая строка без точки в конце. Связанные изменения из разных
  коммитов объединяй в один пункт, мелкие правки вёрстки опускай.
- Описывай то, что заметит пользователь, а не реализацию: без имён
  файлов, классов, компонентов и эндпоинтов. Исключение — раздел
  «Исправления», где допустимы технические названия (`package-lock.json`,
  HTTP-статус).
- Если по сообщению коммита смысл неясен, посмотри его изменения
  (`git show --stat <хеш>`) или `CLAUDE.md`.
- Текст на русском, выведи его одним блоком ` ```markdown `, готовым для
  вставки.
